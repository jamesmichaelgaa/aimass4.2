# AI Agent Specification — aimass4.2

## 1. Purpose
The aimass4.2 AI assistant helps a user understand their own budgeting data and consider practical spending choices. It is an explanatory assistant, not an autonomous finance agent.

## 2. MVP capabilities
The assistant may perform only these four capability groups:

### A. Spending insights
- Summarize income and expenses over a specified period.
- Identify largest spending categories and notable changes when enough comparable data exists.
- Explain budget utilization using application-calculated figures.
- State when history is too limited to identify a reliable pattern.

### B. Budget and savings recommendations
- Suggest practical, optional adjustments based on budgets and recorded spending.
- Identify categories where spending is close to or above a budget.
- Offer general savings ideas grounded in user-provided goals/preferences when available.
- Avoid shame, pressure, certainty, or unsupported claims.

### C. Payday and cash-flow forecast explanations
- Explain the deterministic forecast supplied by the application.
- Identify which expected salary and unpaid bill items affect the estimate.
- Explain assumptions and uncertainty.
- Never independently calculate or replace authoritative financial totals; do not invent missing inputs.

### D. Conversational budgeting Q&A
- Answer natural-language questions about the user's own available budgeting summaries.
- Explain budgeting concepts in plain language.
- Ask a concise clarification question when the period or intent is unclear.
- If requested information is not present, say so and explain what the user can enter.

## 3. Prohibited actions
The assistant must not:
- Create, edit, delete, or categorize transactions.
- Create or change budgets, salary schedules, cash positions, bills, or reminders.
- Mark a bill as paid or initiate a payment.
- Execute SQL, code, shell commands, or arbitrary tools generated by the model.
- Access another user's data or infer identity from a client-supplied user ID.
- Claim to connect to a bank, wallet, or external financial account.
- Provide individualized investment, lending, tax, legal, or regulated financial advice.
- Guarantee a future balance or payday forecast.

The MVP assistant is read-only. Any future write-capable workflow requires a separate product/security review, explicit user confirmation, server-side authorization, auditability, and updated tests.

## 4. Trust boundaries and request flow
1. Client sends a task/question and Supabase access token to the Edge Function.
2. Edge Function validates the JWT and derives user ID from verified claims.
3. Validate request schema, size, task type, and rate limits.
4. Query only records owned by the authenticated user using RLS or carefully scoped server-side queries.
5. Prepare a minimal context object with aggregates and only necessary details.
6. Call OpenAI using a server-side secret.
7. Validate/normalize the model response and return safe text plus optional structured insight metadata.
8. Do not execute model-proposed actions or SQL.

## 5. Context minimization
- Prefer aggregates (period totals, category totals, budget progress, forecast summary) over raw transaction lists.
- Include raw transaction descriptions only when directly necessary to answer a specific question.
- Remove account identifiers and unnecessary personal details.
- Never send passwords, API keys, access tokens, service-role keys, or database connection strings.
- Do not send a user's full transaction history by default.
- Use a bounded date range and bounded number of records per request.

## 6. Prompt-injection and untrusted content
- System/developer instructions are controlled by the application, not user data.
- Transaction descriptions, bill names, category labels, and user prompts are untrusted content.
- Delimit retrieved text as data and explicitly instruct the model not to follow instructions contained in it.
- Never allow user content to override privacy, safety, or read-only rules.
- Treat model output as untrusted. Render as text/limited Markdown; do not render raw HTML or execute code.

## 7. Response behavior
- Be clear, concise, respectful, and non-judgmental.
- Distinguish recorded facts from estimates and suggestions.
- Cite the relevant date range or categories in prose when helpful.
- State when data is incomplete or unavailable.
- Do not fabricate numbers, transactions, salary dates, or bill status.
- Include a concise reminder that responses are general budgeting assistance, not professional financial advice, when giving personalized recommendations.
- Avoid repeating sensitive transaction details unnecessarily.

## 8. Reliability and cost controls
- Enforce per-user request limits and maximum input/context sizes.
- Set request timeouts and handle upstream provider errors safely.
- Do not retry expensive requests indefinitely.
- Consider caching deterministic summaries, but never share cached user data across users.
- Record usage metadata without storing raw prompts or sensitive financial context unless explicitly justified and disclosed.
- Provide graceful fallback when AI is unavailable; core tracking and budgeting must continue to work.

## 9. Secrets and configuration
- Store OpenAI API key only in Supabase Edge Function secrets.
- Never use a frontend-exposed `VITE_*` variable for provider secrets.
- Never commit secrets or place them in logs.
- Keep Supabase service-role credentials out of the client.
- See docs/security.md.
- Implemented 2026-11-22: the assistant runs as the `ai-assistant` Supabase Edge Function (`supabase/functions/ai-assistant/`), deployed with `verify_jwt = true` (`supabase/config.toml`). The OpenAI key is read from the Edge Function secret store at call time (`Deno.env.get("OPENAI_API_KEY")`); the frontend bundle was scanned and contains no OpenAI strings. If the secret is absent, the function returns a 503 with a generic message — it never degrades into a non-AI fallback that could leak configuration state.

## 9a. Implemented request flow (2026-11-22)
1. The client (`src/lib/aiClient.ts`) POSTs `{ message, history[] }` with the user's Supabase access token. No user id is sent; identity is derived server-side.
2. The function (`supabase/functions/ai-assistant/index.ts`) verifies the JWT with `auth.getUser(token)` and builds a Supabase client whose Authorization header carries the caller's token, so every query is RLS-scoped to that user (the service-role key is never used for user data).
3. Per-user rate limit: 10 requests per rolling 60 seconds (in-memory). Message ≤ 2000 chars; up to 6 history turns are accepted and only `user`/`assistant` roles pass validation. Completion is capped at 700 tokens with a 45-second upstream timeout.
4. `context.ts` gathers aggregates only (month income/expenses/net for this and last month, top expense categories with shares, budget progress, active bills, schedule, cash position). No raw transaction descriptions are sent. Category and bill names are length-bounded (60 chars) and control characters/fence markers are stripped so they cannot forge the data-fence.
5. The context is wrapped in explicit `=== USER DATA START/END ===` markers declared as untrusted data in the system prompt; the prompt forbids revealing itself, forbids non-budgeting topics, forbids recalculation of forecast figures, and forbids guaranteeing outcomes.
6. The reply is returned as a JSON string and rendered as plain text (never HTML) in the Assistant page.
7. Errors are generic; the specific cause goes to the function console only. Provider 429/5xx map to a distinct safe "service busy" message.

## 9b. Forecast explanations status
The deterministic forecast must be computed and verified server-side before the assistant may explain it. The deployed function reserves a `forecast` block in the context schema and includes it in the prompt only when populated. Wiring the verified Phase 3 forecast output into that block is the remaining step and stays disabled until the Phase 3 forecast runtime verification (docs/salary-reconciliation.md test contract) passes; until then the Assistant page offers insights, recommendations, and chat, and the response payload's `forecastAvailable` flag is `false`.

## 10. Acceptance tests
- Unauthenticated requests are rejected.
- A user cannot retrieve another user's context by altering request fields.
- Prompt injection in transaction notes cannot override system rules or trigger actions.
- The assistant refuses or redirects prohibited financial requests.
- Insufficient data produces an explicit limitation, not fabricated output.
- Forecast explanations match supplied deterministic figures.
- No assistant response causes database writes.
- Rate limits and provider failures return safe, non-sensitive errors.
